# 微信小游戏体验版、包体与视频结论

记录日期：2026-08-27

## 体验版二维码最低前提

体验版二维码不是本地构建即可生成。最低闭环为：

1. 已注册并认证（或具备相应开发权限）的微信小游戏主体，且拥有有效小游戏 AppID。
2. 开发者已被该 AppID 的管理员加入成员并授予开发权限；用于扫码体验的微信号也必须在该小游戏的体验成员名单中。
3. 使用官方微信开发者工具或官方 Unity 微信小游戏转换 SDK，按该 AppID 构建并上传代码包。
4. 在微信公众平台小游戏后台将已上传版本设为体验版，再生成体验版二维码；扫码者以已加入的体验成员微信号扫码。

结论：没有 AppID、小游戏后台权限、体验成员配置和一次成功上传，就不存在可供外部扫码的体验版二维码。Android APK、裸 WebGL 包和本地预览二维码均不能替代小游戏体验版二维码。

## 云开发是否必须

不是必须条件。纯本地运行的教学交互小游戏可不启用微信云开发：体验版上传、二维码生成、基础包加载均不以云开发环境为前提。

仅在需要云函数、云数据库、云存储、用户侧持久化数据、服务端鉴权或由云存储承载受控资源时，才需要创建并配置云开发环境。当前项目的 AI 问答若继续调用外部 DeepSeek 服务，仍需单独解决小游戏网络域名白名单、HTTPS、鉴权密钥不可下发到客户端及服务端代理问题；这不等同于“云开发强制”，但实际生产接入通常需要自有后端或云函数作密钥代理。

## 首包/总包官方口径

微信小游戏应采用小游戏分包口径，不采用普通微信小程序“主包 2 MB”的限制。当前应按以下预算执行：

- 首次下载的主包（首包）不超过 4 MB。
- 单个分包不超过 4 MB。
- 主包与全部分包的代码包累计不超过 20 MB。

这里的“代码包”包含随小游戏构建产物进入各包的脚本、场景、配置和被打入包内的资源；远程资源不应作为规避合规审核或关键首屏可用性的手段。微信平台规则可能按工具/基础库版本调整，实际上传前须以微信开发者工具的构建/上传校验和该 AppID 后台提示为最终准据。

## 视频远程化建议

当前 Unity 项目包含 M1 引导和常驻数字人视频，视频通常是首包超限的首要风险。建议：

1. 不将非首屏必须的视频打入主包；主流程先使用必要的静态首帧、海报或轻量占位资源。
2. 将引导视频、数字人视频和可选讲解视频置于项目自有 HTTPS/CDN，使用可审计、稳定且已配置小游戏合法域名的地址；不使用临时网盘或不可控第三方直链。
3. 进入对应教学步骤后再异步下载/预加载，展示明确加载与失败重试状态；视频未就绪时不阻断基础交互流程。
4. 对视频进行移动端编码和码率控制，按实际目标时长/分辨率产出多份资源；保留低码率降级版本。开发阶段可先将视频放在转换 SDK 支持的远程资源/CDN 流程中验证，再确定正式资源管线。
5. 验证 Unity 微信小游戏转换 SDK 对现有 `VideoPlayer`、RenderTexture、LumaKey shader 和远程视频格式/跨域/缓存的实际支持。若原生 `VideoPlayer` 不受支持，改用该 SDK 提供的视频能力或微信小游戏原生视频组件，并保持现有 UI 交互合同。

远程化只适合可延迟获取的大体积媒体。启动所需代码、首屏关键交互资源及离线降级路径仍必须受首包 4 MB 预算约束。
