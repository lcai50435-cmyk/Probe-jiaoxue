## 2. 问题一：引导视频和字幕没有出现，遮罩存在且无法点击

### 2.1 现象

体验人员通过体验版二维码进入 M1 后：

- M1 教学页面已经显示；
- 引导视频人物没有出现；
- 引导字幕没有出现；
- 引导遮罩仍存在，页面按钮无法点击；
- 从用户视角表现为界面已经打开，但交互被卡住。

### 2.2 当前代码行为

`M1IntroVideo` 在进入 M1 时会：

1. 设置 `Time.timeScale = 0`；
2. 激活引导遮罩并拦截输入；
3. 暂时隐藏常驻数字人；
4. 对 CDN URL 视频执行 `VideoPlayer.Prepare()`；
5. 只有收到首帧回调后，才显示半黑背景、视频画面和字幕；
6. 视频结束、报错或超时后，才关闭遮罩并恢复交互。

因此，“教学页面可见但视频/字幕不可见，同时所有按钮不可点击”与“引导播放器仍处于准备/等待首帧状态”高度一致。

### 2.3 原因分析

#### 高可能：iPhone 微信环境没有正常触发 VideoPlayer 首帧链路

当前视频 URL 可访问、文件存在、格式为 H.264 `yuv420p`，并且 MP4 已完成 fast-start 处理。由此可排除：

- 引导文件未上传；
- URL 返回 404；
- 旧 MP4 的 `moov` 索引仍在末尾。

仍需重点怀疑微信 iOS 环境下的 `VideoPlayer + URL + RenderTexture` 链路：

- `prepareCompleted` 没有触发；
- `frameReady` 没有触发；
- 微信 iOS 视频解码器拒绝或延迟创建首帧；
- VideoPlayer 已报错，但错误日志没有被当前体验证据捕获；
- CDN 响应中的 `Content-Disposition: attachment` 对微信 iOS 视频流式解码存在兼容风险。

这类故障不会阻止 Unity 主页面显示，但会让引导状态机停留在遮罩阶段。

#### 中可能：首帧准备耗时超过用户等待时间或超时状态没有正确落地

引导视频约 21 MB、1080×1450、30 fps、码率约 10.9 Mbps。即使已经 fast-start，iPhone 微信内置运行环境仍需要建立网络、解码器和 RenderTexture。弱网、冷缓存或 iOS 解码资源不足可能使首帧明显延迟。

当前遮罩在准备阶段仍会阻塞按钮，因此只要首帧迟迟不到，用户就会认为程序卡死。若超时协程、VideoPlayer 回调或对象生命周期在 iOS 上发生竞态，遮罩还可能没有按预期退出。

#### 中低可能：引导可见状态恢复存在时序问题

引导视频、字幕、半黑遮罩、常驻数字人之间依赖多个回调更新 `Graphic.enabled` 和 active 状态。iPhone 上的回调顺序若与 Editor/Android 不同，可能出现：

- 视频已经准备，但可见 Graphic 未启用；
- 字幕布局先执行，首帧可见状态后续被覆盖；
- 引导失败后遮罩或交互状态没有完整恢复。

当前仅凭截图无法区分“视频没有解码”与“视频已解码但 UI 没有显示”。

### 2.4 尚缺证据

要把原因从假设提升为结论，需要补充：

- iPhone 型号、iOS 版本、微信版本；
- 从扫码到出现卡住画面的实际等待秒数；
- 微信真机调试 Console 中 `M1IntroVideo` 的 `prepareCompleted`、`frameReady`、`errorReceived` 和超时日志；
- 视频 URL 的真机网络请求状态、Range 请求和耗时；
- 卡住时 `Time.timeScale`、遮罩 active 状态、VideoPlayer `isPrepared/isPlaying/time`；
- 同一台 iPhone 冷启动与二次缓存启动是否一致。

### 2.5 当前判断

该问题是体验版 P0 阻断项。现有证据更支持“微信 iOS 视频首帧/显示状态机未完成”，不支持“素材没有打进包”或“CDN 文件不存在”。在拿到 iPhone 真机日志前，不应继续仅靠调整字幕坐标或重复上传同一视频来试错。

## 3. 问题二：iPhone 在 M1 结束后闪退，微信也一起退出

### 3.1 现象

体验人员在 iPhone 上完成 M1 后：

- M1 结束并准备进入下一环节；
- 游戏直接闪退；
- 严重时微信宿主也一起退出；
- Android 手机执行同一流程没有问题。

### 3.2 当前切场景行为

M1 点击“开始探测”后：

1. 播放通关音效；
2. 使用 `WaitForSecondsRealtime` 等待音效时长；
3. 直接调用 `SceneManager.LoadScene("M2")` 同步切换场景。

M1 销毁时会释放引导 RenderTexture、常驻数字人 RenderTexture，并定向卸载帧图集页；但当前切换前没有独立的资源卸载阶段，也没有记录切换前后的运行内存峰值。

### 3.3 原因分析

#### 高可能：M1→M2 同步切场景时出现 iOS 内存/GPU 峰值，宿主被系统终止

“微信宿主一起退出”比普通 C# 异常更接近进程级崩溃或 iOS Jetsam 内存终止。支持该判断的现有证据包括：

- Android 不复现，问题具有明显 iOS 平台差异；
- WebGL 初始内存配置为 32 MB，并启用分步内存增长；iOS 微信环境对连续内存扩容和峰值更敏感；
- BuildReport 显示 M1 Level 约 `36.0 MB uncompressed`，M2 Level 约 `1.6 MB uncompressed`；此外还有 Unity WebGL 堆、WASM、字体、共享纹理、视频解码器、RenderTexture 和帧图集 GPU 内存；
- M1 待机帧图集页在运行时约占一页纹理内存，引导视频还会占用 1080×1450 RenderTexture 与视频解码缓冲；
- 同步 `LoadScene` 期间，新场景资源分配和旧场景资源销毁可能发生短时重叠；即使 `OnDestroy` 中调用了 Release，也不能仅凭代码确认 GPU/原生视频缓冲已在 M2 分配前完全归还；
- iOS 在内存压力下可能直接终止承载小游戏的微信进程或相关渲染进程，用户侧不一定看到 Unity 异常提示。

因此，内存/GPU 峰值是当前首要分析方向。

#### 中可能：iOS 视频解码器或 RenderTexture 在场景销毁时发生原生层崩溃

M1 引导使用 URL VideoPlayer 与 RenderTexture。即使画面没有显示出来，底层视频组件可能仍处于 Prepare、错误回调或释放过程中。M1 结束后同步销毁对象并立即加载 M2，可能在 iOS 微信视频桥接层形成：

- 视频解码器仍有异步回调；
- RenderTexture 已释放，但底层仍引用；
- VideoPlayer 禁用、Stop、Destroy 与场景加载顺序冲突；
- iOS 硬件解码器资源回收不及时。

这也能同时解释“引导异常”和“M1 结束时宿主崩溃”可能属于同一条视频生命周期问题，而不是两个完全独立的问题。

#### 中可能：WebGL 堆增长或纹理上传在 iOS 上失败

项目当前启用 WebGL 内存增长。进入 M2 时若需要扩展连续 WASM 内存或上传大纹理，iOS 微信环境可能因可用连续内存不足、GPU 纹理预算不足或高性能 Canvas 上下文限制而失败。开发者工具和 Android 的内存模型不同，不能替代 iPhone 真机结论。

#### 低可能：普通 Unity 业务异常或 M2 Scene 缺失

普通 `NullReferenceException`、路径查找失败或 M2 Scene 不在构建列表，通常只会打印错误、停止局部逻辑或表现为加载失败，不太会让整个微信进程退出。M2 已进入当前构建，冻结 Scene 哈希也未变化；Android 能正常进入 M2，进一步降低了这类原因的可能性。

### 3.4 尚缺证据

需要补充以下证据才能定责：

- iPhone 型号、内存容量、iOS 版本、微信版本；
- 崩溃前是否曾看到 M2 任意一帧；
- iOS 系统“分析数据”中的 `JetsamEvent`、WeChat 或小游戏渲染进程崩溃记录；
- 微信真机调试/实时日志中 M1 `LoadScene` 前后的最后一条日志；
- M1 结束前、调用 LoadScene 前、M2 sceneLoaded 后的 Unity 堆、WASM 堆、纹理和总内存；
- 冷启动不播放/播放引导、执行/不执行 AI 问答时是否都复现；
- 同一 iPhone 第二次缓存启动是否仍然复现；
- M1 结束前主动等待视频解码器和 GPU 资源释放时是否仍会崩溃（此项属于后续验证设计，本文不实施）。

### 3.5 当前判断

该问题是体验版 P0 阻断项。当前最可能是 iOS 微信环境中的内存/GPU/视频解码资源生命周期问题，尤其是 M1→M2 同步切场景时的瞬时峰值。由于“微信也一起退出”，在取得 Jetsam/崩溃日志前，不应把问题简单归因于 M2 业务代码。

## 4. 两个问题的关联判断

两个问题可能有关联：

1. M1 引导 VideoPlayer 没有正常完成首帧和播放流程；
2. 底层视频解码器或 RenderTexture 仍可能处于准备、失败或延迟释放状态；
3. M1 结束后立即同步进入 M2；
4. iPhone 在此时出现原生资源回收竞态或内存峰值，导致微信宿主退出。

这只是当前优先假设，不是最终结论。也存在“引导是 VideoPlayer 兼容问题，闪退是独立内存问题”的可能。必须通过 iPhone 真机日志、Jetsam 信息和场景切换内存数据区分。
